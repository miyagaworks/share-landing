## B.【最重要】Super の検証手法に欠陥があった

<risk level="high">
### B-1. git diff から削除行を抜き出すパターンが箇条書きを除外していた

フェーズ5から使ってきた以下のパターンには**構造的な穴がある。**

```bash
git diff -U0 | grep "^-[^-]"   # ← 誤り
```

`^-[^-]` は「先頭が `-` で2文字目が `-` 以外」を意味する。
Markdown の箇条書き（`- ` で始まる行）は diff 上で `-- ` となるため、
**このパターンでは1件も拾えない。**

<known-fact>
当セッションで実証。実際の削除55行に対し、このパターンは36行しか拾わず、
**19行を見落とした。** 見落とした中には「実在しない機能（CRM連携）の削除」
「無料プランの記述の削除」など、確認が必須の行が含まれていた。

Super は一度「CC の報告（34件）は実測（36件）と違う」と誤って指摘した。
正しかったのは CC の報告のほうだった。
</known-fact>

**正しいパターン（次セッションはこれを使うこと）:**
```bash
git diff -U0 | grep "^-" | grep -v "^---"   # 削除行
git diff -U0 | grep "^+" | grep -v "^+++"   # 挿入行
```

件数は必ず `git diff --stat` の insertions / deletions と突き合わせて検算する。
**一致しなければ抽出パターンが誤っている。**

<risk>
フェーズ5でも同じ誤ったパターンを使っている。
対象が `.tsx` だったため箇条書きは少なかったが、
**JSX 内の `- ` で始まる行を見落としていた可能性が残る。**
フェーズ5の2コミット（1e3cc0d / 636a1ea）は、
気になる場合のみ正しいパターンで再確認すること。
</risk>
</risk>

## H. 引き継ぐ判断基準

<known-fact>
フェーズ5 §I（表現の判定基準 / 一般論として残す文面基準 / 触ってはいけないもの /
Cloudflare の設定 / やらないこと）は**すべて有効。変更なし。**

当セッションで追加する基準:

### H-1. 根拠のない訴求バッジの扱い

「安心してご利用いただけます」のような見出しの下に並ぶ短い札は、
断定形の文ではないため語尾ベースの抽出に引っかからない。
**裏付けとなる説明がサイト内に1つもない札は削除する。**

判定に使った基準:
- 裏付けの記述がサイト内にあるか（`grep -rn` で実測）
- 測定可能な事実の断定か（速度・安全性は測定していないなら書けない）
- 実装の実態があるか（「素早い導入」は3ステップ登録という実態があるため残置）

### H-2. 社内資料が古くなったときの扱い

矛盾記述を1つずつ直しても、1年経てば同じ状態になる。
**資料の冒頭に「いつの資料か」「最新の方針はどこを見るか」を明記することを恒久対策とする。**

役目を終えた実装の指示書は、書き直さずに注意書きと打ち消しで凍結する。
書き直すと引き継ぎノートの未対応事項と二重管理になる。
</known-fact>
