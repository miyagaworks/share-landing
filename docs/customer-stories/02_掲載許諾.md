# 掲載許諾の取り方

<context>
`01_依頼文.md` への返信でコメントを頂いた後、公開までの間に踏む手順。
ここを飛ばすと、法令面でも人間関係の面でも取り返しがつかなくなる。

前提となる法令整理は `README.md` §2・§3・§7。
</context>

---

## 1. 一番大事なこと

<risk level="high">
**許諾は「文面を見せてから」取る。**

依頼の返信に「掲載していいですよ」と書かれていても、**それだけでは足りない。**
相手はまだ、自分の言葉がどう切り取られ、どう見えるかを知らない。

段取りとしては下記の 手順3 が許諾の成立点であって、手順2 ではない。

やりがちな失敗:
- 依頼の返信をもって許諾とみなし、そのまま公開する
- 文章を整えてから公開し、事後に「こう載せました」と伝える
- 「載せてよいですか」とだけ聞いて、載せる形を見せない

いずれも、後から「そういうつもりではなかった」となる。
相手は取引先である。法令以前に、関係を壊す。
</risk>

---

## 2. 手順

<task>
### 手順1. コメントを受け取る
`01_依頼文.md` の返信を受け取る。
掲載してよい範囲（会社名・役職・氏名・顔写真・ロゴ・リンク）の回答も揃っているか確認する。
抜けがあれば、この時点で聞き直す。

### 手順2. 掲載原稿を作る
実際にページに載る形（見出し・並び順・添える一文まで含む）で原稿を作る。
- 頂いた文面は変えない
- 数値や成果が書かれていた場合の扱いは §5
- 添える一文は `03_ページ設計.md` §3 の確定文言を使う

### 手順3. 最終確認を送り、許諾を得る ← ここが成立点
§3 のテンプレートを送る。
「このまま掲載してよい」旨の返信を受け取った時点で許諾成立。

### 手順4. 返信を保存する
許諾の返信メールを PDF にして保管する（保管場所は §4）。

### 手順5. 公開する
実装は `03_ページ設計.md` に沿って実装CCへ依頼する。

### 手順6. 公開したことを伝える
掲載先の URL を相手に連絡する。
このとき「不都合があればいつでもご連絡ください」と添える。
</task>

---

## 3. 最終確認メールのテンプレート

<task>
手順3 で送るもの。ここで OK を得られて初めて公開できる。
</task>

```

◯◯株式会社
◯◯ ◯◯ 様

先日はご協力いただき、誠にありがとうございました。
頂いたコメントをもとに、掲載原稿を作成いたしました。

下記の内容とかたちで、Share のサイトに掲載したいと考えております。
ご確認のうえ、問題なければ「掲載可」とだけご返信いただけますでしょうか。


──────────── 掲載する内容 ────────────

【掲載ページ】
https://sns-share.com/case-studies

【会社名】
◯◯◯◯

【部署・役職・お名前】
◯◯◯◯

【業種】
◯◯◯◯

【お使いの場面】
◯◯◯◯

【コメント（頂いた文面のまま）】
「◯◯◯◯◯◯◯◯◯◯◯◯◯◯◯◯」

【顔写真】
掲載する ／ 掲載しない

【会社ロゴ】

このセクションの冒頭に、次の一文を表示します。

　掲載しているコメントです。謝礼等の対価はお渡ししていません。」

・ご指摘があれば、いくらでも直します。表現の修正・削除、どちらでも承ります。
・掲載後も、ご連絡いただければ3営業日以内に取り下げます。
・掲載期間の定めは設けておりません。取り下げのご連絡があるまで掲載いたします。
・ご連絡先：info@sns-share.com

お手数をおかけしますが、どうぞよろしくお願いいたします。


────────────────────
株式会社Senrigan
宮川 きよみ
info@sns-share.com
https://sns-share.com
────────────────────
```

<known-fact>
### このテンプレートで押さえていること

| 項目 | 何のために書いているか |
|---|---|
| 掲載ページの URL を明示 | どこに載るか分からないまま同意させない |
| 頂いた文面を丸ごと再掲 | 改変していないことを相手が確認できる（`README.md` §4） |
| 項目ごとに「掲載する／しない」を並べる | 一括同意にしない（`README.md` §7） |
| 添える説明文まで見せる | 依頼して頂いたコメントである旨が表示されることに、本人が同意している状態を作る |
| 「謝礼等の対価はお渡ししていません」を含む | 事実の表明。渡していないからこそ書ける |
| 3営業日以内に取り下げ | 期限を数字で約束する。「速やかに」では守ったか判定できない |
| 掲載期間の定めなし＋撤回自由 | 期限を切ると更新のたびに再許諾が要る。撤回自由で代替する |
</known-fact>

## 4. 記録の残し方

<risk level="high">
### 台帳は、このリポジトリに置かない

顧客の氏名・会社名・許諾状況は個人情報。
**git の管理下に置くと、履歴から消せなくなる。**
取り下げの連絡を受けてファイルを消しても、過去のコミットには残り続ける。

→ 台帳は**リポジトリの外**（社内の共有ドライブ、または宮川さんの手元）で管理する。
このフォルダに置いてよいのは、本ファイルのような**個人名を含まない設計書だけ**。
</risk>

<task>
### 台帳に残す項目

| 項目 | 例 |
|---|---|
| 会社名（正式名称） | 株式会社◯◯ |
| ご担当者名 | ◯◯ ◯◯ |
| 依頼を送った日 | 2026-08-01 |
| コメントを受け取った日 | 2026-08-05 |
| 最終確認を送った日 | 2026-08-06 |
| **許諾を得た日** | 2026-08-07 |
| 許諾メールの保管場所 | （PDF のファイル名・保存先） |
| 掲載してよい範囲 | 会社名○／役職○／氏名○／顔写真×／ロゴ×／リンク○ |
| 対価の有無 | なし |
| 掲載開始日 | 2026-08-10 |
| 掲載 URL | https://sns-share.com/case-studies |
| 取り下げ日 | （あれば） |

「対価の有無」の欄は、常に「なし」になるはず。
**ここに「なし」以外が入ったら、掲載の設計をやり直す**（`README.md` §3）。
</task>

## 5. コメントに数値が書かれていた場合

<task>
相手が善意で「問い合わせが増えました」「◯件受注できました」と書いてくださることがある。
そのまま載せられない（`README.md` §5）。かといって黙って削るのは改変になる（同 §4）。

**正直に事情を伝えて、書き直しをお願いする。**

```
ありがとうございます。大変ありがたいお言葉なのですが、
広告表示のルール上、成果の数値を掲載するには
「全利用者のうち何割の方が同様の結果になったか」という調査データが必要になります。

弊社にはそのデータがないため、恐れ入りますが該当箇所を外したかたちで
掲載させていただけますでしょうか。

具体的には、下記の部分です。
「◯◯◯◯◯◯」

この一文を削るか、数値を含まない表現に書き換えていただけますと幸いです。
どのように直すかは、◯◯様のお言葉でお決めいただければと思います。
```

書き換えを**こちらで案文にして送らない**こと。相手に決めてもらう。
こちらが案文を出すと「事業者が表示内容の決定に関与した」形になる（`README.md` §2）。
</task>

---

## 6. 取り下げの連絡を受けたとき

<task>
1. 受けた当日中に「承知しました。3営業日以内に取り下げます」と返信する
2. 該当箇所を削除する変更を実装CCに依頼する
3. 公開後、取り下げが完了したことを相手に連絡する
4. 台帳に取り下げ日を記入する

理由は尋ねない。尋ねると引き止めの圧力になる。
</task>

## 7. やってはいけないこと

<risk level="high">
| してはいけないこと | なぜ |
|---|---|
| 依頼の返信をもって許諾とみなす | 載る形を見せていない（§1） |
| 文面を整えてから、事後に報告する | 改変にあたる（`README.md` §4） |
| 良い意見だけを抜き出して載せる | 恣意的な抽出にあたる（同上） |
| 謝礼・割引・優待を渡す | 対価にあたる（`README.md` §3） |
| 「載せてくれたらリンクを貼ります」と持ちかける | 対価性が生じる（同上） |
| 数値の書き換え案をこちらから出す | 内容の決定に関与した形になる（§5） |
| 台帳をこのリポジトリに置く | 個人情報が git 履歴に残る（§4） |
| 断られた相手に再度お願いする | 圧力になる（`01_依頼文.md` §3-2） |
</risk>
</content>
